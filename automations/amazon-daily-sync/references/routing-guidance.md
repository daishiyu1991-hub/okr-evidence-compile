# Routing Guidance — 5 个归属选项详细说明

> 用户在 [REVIEW QUEUE] 回 "5 解释 X" 时, codex 输出对应说明.

---

## 🚦 task — 每周任务

### 定义

写到 `🚦每周任务` Base 表 (tblrduPxvdifLm62) 的一条 record. 单点动作, 本周内可完成.

### 何时归这里

- 单一动词动作: "跟 / 发 / 写 / review / 整理 / 调研 / 跟进 / 同步"
- 时间尺度: ≤ 1 周
- 不需要分阶段 / 多步骤

### 何时不该归这里

- 跨周大事 → 归 `🧮 团队项目` 或 `📊 项目活动`
- 不需要新 record, 只是状态变更 → 归 `📝 仅 audit`

### 例子

✅ "跟林军 sync Sorftime 子账号问题"
✅ "发 PRD V1 给罗国华 review"
✅ "调研 3 个唤醒灯竞品 listing"
✅ "整理本周经营复盘材料"
✅ "上线本周新品 listing"

❌ "做一个自动周报 workflow" → 团队项目 (跨周建设)
❌ "完成目标管理 AI 化集成" → 团队项目 (大事)

## 📊 项目活动 — 项目活动管理

### 定义

写到 `📊项目活动管理` Base 表 (tblf54mtW07iPCRL) 的一条 record. 某既有 🧮团队项目 的一个"阶段". 2-4 周, 跨多步骤.

### 5 个项目阶段 (select 字段值)

| 阶段 | 内容 |
|---|---|
| `1-确定目标` | 明确这个项目要做什么, 边界, 不做什么 |
| `2-确认需求` | 调研, PRD, 用户访谈, 竞品分析 |
| `3-方案设计与规划` | 技术方案, 资源分配, 时间线 |
| `4-实施并上线` | 真正执行, 落地, 上架 |
| `5-汇报总结` | 复盘, 文档, 分享 |

### 何时归这里

- 候选事项跨多周 (2-4 周)
- 含多个子任务可拆
- **属于一个既有项目的某阶段** (evidence 里 mention 了某 🧮团队项目 id 或项目名)
- 例子文本含: "X 项目的 Y 阶段" / "完成 X 的 Z 部分" / "X 项目的 PRD 设计"

### 何时不该归这里

- 没对应的既有项目 → 应先用 `🧮团队项目` 起草新项目
- 单点本周内 → 归 `🚦 task`
- 团队项目本身 → 归 `🧮 团队项目`

### 例子

✅ "ai 唤醒灯 · 阶段 2 PRD 设计" (有既有 ai 唤醒灯项目)
✅ "完成红光面部理疗项目的实施阶段"
✅ "目标管理 AI 化项目的方案设计与规划阶段"

❌ "做一个全新 X 工具" → 团队项目 (无既有项目)
❌ "本周写 X PRD" → task (单点)

### ME 你 base 现状

```
你 own 的项目活动: 1 条 "ai 唤醒灯开发" (持续到 2026-08-31)
```

大部分既有团队项目实际跳过这一层. 引入新项目活动时考虑: 这个事真需要明确阶段标记吗? 简单项目可直接挂 task.

## 🧮 团队项目 — 团队项目清单 (草稿)

### 定义

写到 `🧮团队项目清单` Base 表 (tblOHGg4IA2pY7uh) 的一条 record. 1-6 个月大事, 跨多阶段.

### ⚠️ cron 模式下不直接建 base record

**自动化时此选项实际只起草 wiki 草稿, 不写 base**.

具体 cron 跑到此 routing 时:
1. 写 wiki 草稿到「01 目标与项目管理 / OKR 巡检与草稿区」节点下
   - title: `团队项目草稿 · <事项前 30 字> · YYYY-MM-DD`
   - 内容: 项目名 / 目标 / 候选关联KR / 候选成员 / 拟拆活动 / 来源 evidence
2. lark-im DM owner: "今天 evidence 出现项目级 candidate: <事项简称>. 已起草 wiki: <link>. 请到 🧮团队项目清单 base UI 手动建 record."

Owner 第二天到 base UI 看 wiki 草稿, 决定是否真建项目.

### 何时归这里

- 候选事项跨 1-6 个月
- "做一个 X 工具 / 平台 / 系统 / 产品"
- 含明确多阶段 (设计 / 开发 / 上线 / 复盘)
- 影响范围大, 应该升级到 OKR 级承诺
- 例子文本含: "做一个" / "建一个" / "完成 X 的整套" / "搭一个 X 体系"

### 何时不该归这里

- 单点 → `🚦 task`
- 既有项目的某阶段 → `📊 项目活动`

### 例子

✅ "做一个自动周报 workflow" → cron 起草, owner 决定
✅ "完成目标管理 AI 化, 集成到面板"
✅ "ai 唤醒灯产品研发"
✅ "做一个 OKR 自动同步 系统"

## 📝 仅 audit — KR/项目 audit 字段刷新

### 定义

不建新 record, 仅更新 ME-owned 相关 record 的 audit 字段:
- `最近更新原因` = source + summary
- `最近更新时间` = now
- `最近更新来源` = evidence link
- `AI编译摘要` = ≤ 80 字摘要
- `待人工确认` = `true`

**不动正式状态字段** (KR.状态/进度/输出结果, 项目.正式进度).

### 何时归这里

- 群里 / 会议 mention 某 KR / 项目状态变化, 但当前已有对应 record → 仅刷新 audit
- 高 confidence "完成了" / "进度到 N%" 信号 → audit + surface 给 owner 让他手动改 formal
- evidence 信息有价值但不构成新行动项

### 何时不该归这里

- 真有新行动项 → 应该归 `task` / `项目活动` / `团队项目`
- 闲聊跑题 → 归 `skip`

### 例子

✅ 群里说: "KR1 实际进度 50%, 不是 0%" → 刷新 KR.audit + 摘要"群中 mention KR1 进度 50%" + 待人工确认=true
✅ 会议提: "项目 X 这周阻塞 = 等供应链" → 刷新项目.audit + 摘要"群中提阻塞: 等供应链"
✅ 群里讨论某 KR 但没明确动作 → 刷新 KR.audit 记录"今天群里讨论了 KR"

### Confidence 判断

- High: evidence 字面明确 (如 "完成了" / "进度 N%" / "状态改 X")
- Low: evidence 含糊 (如 "可能改一下" / "感觉得变" / "下次再议")

High confidence 时 audit 段会 surface "建议你下次 manual 跑 / base UI 手动改 formal X 字段".

## ⏭️ skip — 不写

### 定义

不写任何 record, 不输出 audit. evidence 仅 read 完, 不留 base trace.

### 何时归这里

- 闲聊 / 玩笑 / 跑题
- 跟业务无关 (生日 / 周末计划 / 八卦)
- 误抓 (如 ME 自己的转发 / 引用别人的话, 不是 ME 的行动项)
- 重复 (跟既有 task 完全同义, 不需要新 record)

### 例子

✅ 群里说 "周末聊聊乡村振兴" → skip
✅ ME 转发别人的链接 "看看这个 article" → skip (除非 ME 明确说 "我要做")
✅ 玩笑话 "我去当外卖员算了哈哈" → skip

### 注

skip 不代表"忽略 evidence". evidence 仍在 read 后被记入 audit log (本次扫的 chat / meeting 都记下来). 仅是 base 不新增 record.

## 三层关系总结

```
🧮 团队项目  =  一本书   (季度目标, 1-6 个月)
📊 项目活动  =  章节     (阶段, 2-4 周)
🚦 每周任务  =  段落     (单点动作, ≤ 1 周)
```

简单项目可走两层 (团队项目 → 任务, skip 项目活动);
≥ 3 月大事才用三层完整结构.

## 决策流程图

```
candidate 来了:
   │
   ├─ 单点动作, 本周内做完?
   │    └─→ 🚦 task
   │
   ├─ 是既有项目的某阶段 (≥ 2 周)?
   │    └─→ 📊 项目活动
   │
   ├─ 跨多月新方向 (没对应既有项目)?
   │    └─→ 🧮 团队项目 (起草, 等 owner 手动建)
   │
   ├─ 不是行动项, 只是状态信息?
   │    └─→ 📝 仅 audit
   │
   └─ 跟业务无关 / 闲聊?
        └─→ ⏭️ skip
```
